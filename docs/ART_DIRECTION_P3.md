# P3 美术与摄影机规范 — 低多边形、Q 版、真正 Three.js

> 本文锁定用户明确选定的**第二张 Q 版低多边形《侵略者》概念图**的美术方向。它是目标参考，并不等于已实现的 WebGL 渲染。关联 [P3 总枢纽 #34](https://github.com/SiliconYC/React-SpaceInvader/issues/34)、[任务分组](ROADMAP_P3.md)。本次文档提交不声称已经生产或入库任何新图片/模型。

## 视觉目标

不是复刻电影级写实图，也不是幼稚的纯几何教学 Demo，而是**精致、圆润、轮廓鲜明、颜色克制的 Q 版低多边形科幻街机游戏**。优先保证可玩性和单位/弹道辨认，再用模型体积、灯光与背景丰富质感。

- 玩家：白蓝色饱满机身 + 加大宽翼 + 深色舱盖 + 两枚浅青色发光尾喷；从屏幕前方清晰辨认。
- Scout：小巧轻盈、尖翼/单传感器，暖橙金；Raider：更宽更红、两侧武器/机械舱；Guardian：稳重粗壮、紫色装甲和发光能量核心。**三者不能只是换色**。
- 材质：少量共用 MeshStandardMaterial，塑料/陶瓷式的半哑光机身、适度金属高光、少量 MeshBasic/发光材质；有必要才做少量圆角倒角。避免噪声纹理、法线贴图、成百个螺丝细节、廉价霓虹包边。
- 建议调色起点（仅作为色板，不是最终硬编码）：背景深蓝 `#07152B`、微紫 `#221A43`；玩家蓝白 `#E9F5FC`、青 `#58DDF3`；Scout 暖橙 `#FFB86B`；Raider 珊瑚红 `#E67A7D`；Guardian 淡紫 `#A99ADF`。灯光和真实 sRGB 输出下再微调。
- 任何额外装饰必须支持“少即是多”：较高亮度、对比度、动态频率始终留给玩家、敌机和弹道。

## 战斗平面、摄影机与模型姿态

1. 游戏真实世界继续仅有 `(x,y)`：舰船和双方子弹的逻辑 pivot 在同一 `z=0` 战斗平面。**正常战斗时，此平面平行屏幕**，相机视轴垂直该平面。逻辑、命中盒、物理时间步、编队保持既有实现。
2. 首选 **小视场角、远相机的 PerspectiveCamera**。可尝试 FOV 约 15–25°，但必须由真实纵横比推导相机距离与视场，不机械复制某个数值。相机位置在平面法线上且 lookAt 战场中心。与平面上所有单位具有同一距离，所以其逻辑中心在不同 XY 位置不应出现近大远小；透视仅体现在模型的**三维厚度**、背景深度与转动时的表面变化。
3. 与现有 OrthographicCamera 做真实截图和屏幕投影对照。若弱透视使射击瞄准、边缘位置、手机显示显著退步，允许保留正交相机，并通过**实体模型厚度、局部姿态和背景分层**实现三维感。
4. 玩家左右移动允许屏幕内倾斜约 8–15°、真实三维滚转约 3–8°、轻度俯仰与弹性回正；悬停时不同轴小幅低频摆动。敌机同类动作共享风格、可加稳定 ID 相位错开。模型旋转只在渲染节点或 Instance Matrix 合成，**绝不让 hitbox 随旋转变化**；弹丸生成逻辑仍以原有 XY 发射点为准。
5. 正常作战禁止大幅运镜、倾斜整张玩法平面或让敌弹方向随视觉镜头改变；切波次/结算可短暂运镜，尊重减少动态效果设置。

## 三维分层、背景与遮挡

| 层 | 实现 | 规则 |
| --- | --- | --- |
| 超远层 | **生成的二维银河/星云 WebP** + 远星点 | 低对比，不包含事先烘焙的舰船/敌人/HUD/土星/岩石 |
| 天体层 | 低面数 **3D 球体 + ring mesh** | 带环天体置于边缘/右上角，轻微真实自转，不遮挡交战 |
| 环境层 | 几种共享网格的 3D 低模陨石 | 缓慢、低频漂移和转动；浅视差；可实例化 |
| 交战层 | 玩家、敌机、双方子弹、命中粒子 | 最清晰、优先绘制，逻辑 XY 同平面 |
| 边缘装饰层 | 看起来靠近镜头的大低模岩石 | 仅在屏幕角落/侧边；**绝对不能跨过单位、弹道、触控 HUD**；越界自动隐藏或裁剪 |
| 最前 HUD | DOM/CSS + 少量 SVG 图标 | 小尺寸、少文字、横竖屏不侵占战场 |

近景岩石要有 3D 体积，但不能真让深度测试遮挡交战层。使用遮挡安全区/独立合成/遮罩；在窄屏时优先降低密度或完全隐藏，不坚持“必须看见大岩石”。避免全场景昂贵景深；可用少量分层软化效果，禁止让主单位失焦。

银河/星云优先使用真实生成图像；天体、陨石和飞船必须是真实可旋转的 Three.js 网格，不能以大张 2D 游戏截图模拟游戏。背景运行时允许缓动，但不得产生与敌人相似的发光飞行物。

## 生成资产必须真实入库

- **源与输出同时留痕**：图像生成工具产出后，将 **实际原始图**（PNG 或可追溯源）和优化后的 WebP/PNG 游戏文件提交仓库。建议 `docs/art/sources/` 保存参考与原图，`public/art/backgrounds/` 保存网页实际使用的优化文件；对比说明放 `docs/art/`。生成式资产注明生成工具/时间、编辑处理和许可/再分发说明。
- **模型必须源码化**：首选 Git 中 Three.js 参数化网格（`src/render/`、`src/art/`）；如生成 GLB/GLTF，则提交 **真实模型文件** 以及可编辑原始模型/生成脚本、导出步骤与使用授权。不能只提交照片、概念图、外链或宣传视频。
- 每个 PR 应指明素材 Git 路径、体积、贴图加载代码、同源 Vite BASE_URL 规则、正常页面的真实浏览器截图以及逻辑回归。图片不是 Three.js 模型；不能把概念图当最终渲染截图。
- 建议单张运行时背景 WebP 控制在约 300KB（需有图片质量和加载速度实测再确定）；不得为实现一张概念图无节制引入复杂贴图、外部 CDN、沉重后处理。GPU 资源几何/材质共用并正确 dispose。
- **参考图状态**：第二张概念图目前只在此前对话中被用户确认；仓库正式参考图应由 #37 **实际提交 Git** 并提供文件链接，在此之前不得声称已经归档。#42 须实际生成不含前景实体的银河图并提交 Git。

## 正式验收

正常 Pages 运行应能区分：参考概念图、Git 中真实资产、Three.js 的浏览器原生截图。每次 Issue 必须核对可读性、遮挡、1024px 以上桌面、手机横竖屏、子弹命中、长时间性能与资源回收。强制沿用 P1/P2 功能与数据驱动、触屏、音频和本地排行。

本阶段只改视觉和可选视觉主题数据；不增加三维游戏操作，不新造引擎，不堆控制台 UI，不为美观牺牲有效战斗视野。
