## 1. 结论与要达到的画面

当前问题不是“没有使用真正的 Three.js”，而是**已有三维形体和动作没有被组织成足够鲜明的美术表达**。代码里有机翼厚度、凸起舱盖、光学眼、姿态、粒子和镜头，但正常观看时，玩家仍容易把它理解成星空贴图上的小图标阵列。继续增加零件、正弦摆动、光圈或后处理，并不能自动消除这种观感。

推荐方向是**有重量的 Q 版太空玩具剧场**：乳白与蓝青的短胖玩家机，橙色独眼侦察机，珊瑚红双武器袭击机，紫色厚甲守卫机；主体具有清楚的体块转折和少量宽高光。背景由一个有构图作用的三维天体、稀疏的远景和安静的银河组织起来。移动能读出起势、承力和回稳，开火有机械反应，击毁有结构解体；胜败通过飞船本身的表演成立。

玩家在前几秒应看见飞船的厚度和性格，按一次方向键应感到推力，击落一架敌机应看懂发生了什么。即使关闭粒子和发光，形体、构图和动作仍要成立。仍然完整保留经典 XY 规则：画面立体不以纵深操作为代价。

## 3. ReactMono 值得学习的具体内容

### 3.1 它的立体感由相互支持的关系形成

角色有大头、身体、突出的口鼻和手臂；房屋有屋檐、墙面和门窗，钟楼提供高度锚点。斜俯视同时展现顶面与侧面。暖主光和统一投影把这些体块放在同一个空间里。薄道路、地块和岛体又提供共同尺度。形体不复杂，但读起来是一个小世界。

SpaceInvader 不具备棋盘地面，却可以建立同样可靠的关系：舱盖与翼根的高度差、装甲与凹槽的遮蔽、同一个主光方向下的机身明暗、远景与主体的色彩距离、起步时局部零件的滞后。不能把“太空没有地面”理解成可以完全放弃体块之间的光影联系。

### 3.2 动作表达的是角色正在做什么

源码中角色跳步按路段组织，包含方向变化、抬升、落点和相机跟随；胜利是角色举手和跳跃，失败是倾倒、下沉和缩小。身体、手臂、道具与镜头共同讲一个事件，而不是所有对象永远做同频摆动。

可借鉴动作分层和起承收，不照搬棋盘移动耗时。实时射击必须按键立即移动、立即发射；重量感应放在机身姿态、翼片、喷口和局部后坐力上，不能靠拖慢输入制造。

### 3.3 不能机械照搬的部分

- 小镇本身使用**正交相机**，因此“换成透视就高级”不成立。SpaceInvader 正常战斗继续保持 XY 平面与屏幕平行；不复制小镇的斜俯视角。
- 棋盘的地面阴影、跟随镜头、宽大的回合操作卡片有其类型前提。太空射击不新增承影地板，不让战斗镜头追着玩家跑，也不把战场塞进 UI 框。
- 小镇的源代码使用 React Three Fiber；这是组织方式，不是质量来源。本项目现有原生 Three.js 足以承载目标，无需为学习参照而迁移渲染框架。
- 小镇截图也有较大留白，不把它当成所有维度都无条件正确的模板；本项目以战斗可读性和有效画布为准。

### 4.1 需要正视“细节最后只有几像素”

按当前 Stage 投影公式、36×24 世界，以及源码中玩家约 2.36、Scout 约 1.82 的未旋转翼展估算：

| CSS 视口 | 输入假设 | 玩家翼展 | Scout 翼展 |
| --- | --- | --- | --- |
| 1920×1080 | 桌面 | 约 95px | 约 73px |
| 1440×900 | 桌面 | 约 79px | 约 61px |
| 390×844 | coarse 触控 | 约 24px | 约 18px |
| 844×390 | coarse 触控 | 约 27px | 约 21px |

这是公式推算，**不是本轮浏览器实测**；不计姿态、镜头过场和 DPR，DPR 也不会增大 CSS 中的主体。公式为 `像素翼展 = 高度 / spanY × 模型翼展`。触控当前额外预留 7.4 世界单位底部空间，横屏也受到影响。

因此：先优化实际尺寸可读的大形、色块和动作，之后才做近景细节。移动端还要研究把固定的大块预留改为与真实触控安全区相配的投影边距，保持完整战场、等比缩放和原世界尺寸。**不能通过裁掉敌阵或放大模型超出原命中轮廓来掩盖问题。**

## 5. 方向选择与美术总规范

| 方向 | 优点 | 代价与风险 | 建议 |
| --- | --- | --- | --- |
| Q 版太空玩具剧场 | 承接原目标；圆润体块、清洁高光和局部机械动作在小尺寸更易读 | 对比例、倒角、光影和动作设计要求高 | **推荐** |
| 风格化硬科幻模型 | 材质、机械结构与尺度感空间大 | 细节缩小后消失，易落回暗色小图标；制作成本高 | 暂不选择 |
| 霓虹几何街机 | 成本低、可读性容易建立 | 难以回应这次对真实三维审美和动画的要求 | 不作为本轮目标 |

推荐方案保留原有机型身份和主色，改变造型力度与表演质量。色板不继续扩张：背景低饱和蓝紫；玩家乳白/青蓝；敌机暖橙/珊瑚红/紫；危险弹丸使用与背景明确区分的暖亮色，不能仅靠颜色区分敌我。

主体每型控制为一个主壳、一个结构暗色、一个强调色；大致以 70/20/10 的可见面积组织，作为构图草案而非硬测试。小零件在目标缩略尺寸无贡献就合并或删除。保留低模的大形概括，但对舱盖、机鼻和翼根采用合适的平滑法线与倒角，避免把“低模”误解为处处尖锐碎面。

## 6. 模型优化：每种飞船都有主角部件

| 单位 | 建议形体 | 材质与识别点 | 可动画部件 |
| --- | --- | --- | --- |
| 玩家 | 短胖中央机身，饱满肩部，宽翼根向短翼尖过渡；双发动机与机身有明确结合关系 | 乳白主壳、蓝青翼面、深色凸起舱盖；舱盖与机身高光分开，尾喷不是两个发光点了事 | 两侧控制翼片、喷嘴内芯、机腹武器组件 |
| Scout | 豆形主壳与略上挑短翼，明显的单眼凹座；减少像纸飞机的长尖轮廓 | 暖橙主壳、奶油护边、深眼罩；单眼是表情和动作焦点 | 眼球/镜片朝向、短翼的小幅迟滞、尾喷 |
| Raider | 横向双武器舱与瘦腰构成“攻击者”；外侧翼爪和炮口保留一眼可辨的负空间 | 珊瑚红护甲、深色炮舱；避免装甲细条把剪影切碎 | 双炮各自短行程后坐力、翼爪收展，运动不制造额外炮弹 |
| Guardian | 中央厚盾、宽肩、凹陷能量核；靠厚度与阶梯大面表现重，不靠全身缩放脉冲 | 紫灰主甲、奶油高面、深色凹槽；核心是小面积亮点 | 两片装甲的局部受击回弹、核心收缩与熄灭、重型喷口 |

制作顺序为：灰模剪影 → 固定主光下的体块 → 三色材质 → 局部关节 → 动作 → 战斗缩略检查。每型保留正面、3/4、侧面观察，但**正常战斗的正面画面是决定性检查**。

模型逻辑根节点固定在引擎 XY，零件在其下独立变换。可探索小幅基础 pitch/yaw 暴露舱盖、翼厚；角度以显示轮廓和弹道对齐实测收敛，不直接把大角度写死。禁止为展示侧面而绕过机身瞄准关系，禁止把可控 z 引入引擎。

源资产路线：优先复用现有参数化网格；某个关键形体反复难以得到干净表面时，允许后续使用 Blender 做原创模型、法线和局部关节，再导出 GLB。届时 `.blend`、导出文件、步骤、许可与运行时版本一起入库。无需现在重写模型加载或为了“全部代码生成”牺牲造型。

## 7. 材质与灯光：让三维厚度在普通画面里成立

1. **先固定一个灯光样板。** 同画面放玩家和 Scout，在正式相机、正常比例下调试。左上暖白主光、冷蓝较弱补光，背缘光只用于轮廓脱离背景；环境光不能抹平凹槽。逐级验证主体亮面、半影和暗面的分离。
2. **先有反射内容，再讨论光滑。** 目前 clearcoat 数值无法单独保证舱盖好看；后续比较小型同源环境贴图/预过滤环境与当前直射光方案，形成宽而有方向的高光。环境素材源与优化结果入 Git，不依赖 CDN。
3. **明确材质分工。** 主壳半哑光，舱盖较光滑，结构件更暗且反射较弱，金属只占少量。全身 emissive 会抬亮暗面；把持续自发光集中到喷口、镜片、能量核，不能用蓝色描边替代真实受光。
4. **补局部遮蔽，不给太空造地面。** 优先在模型顶点色/小型烘焙遮蔽中表达翼根、舱盖座和装甲缝的关系。若需要动态自阴影，先在样板比较成本、阴影抖动及缩小时的价值，再决定是否使用全场景一致的阴影方案。不能照搬小镇棋盘投影到一张无意义的太空平板。
5. **后处理最后决定。** 不预设必须 Bloom/SSAO/景深。首版比较无后处理与低成本局部辉光；子弹和机身必须锐利，不做全屏模糊、色差或持续震屏。追加效果须提供同条件画面收益和 GPU 开销。

## 8. 背景与构图：做有空间关系的场景

### 8.1 五层保留，内容重新编排

| 景别 | 建议内容与动势 | 约束 |
| --- | --- | --- |
| 极远背景 | 低对比银河云带、稀疏星点；明暗块引向主战区外围 | 仍可用 2D 原创同源贴图；不要靠增加星点密度填满空白 |
| 主天体 | 一个有明确亮暗半球的带环行星，局部离画；环有真实前后关系和厚薄层次 | 真实 3D；位置服务构图，不和玩家争抢最高亮度 |
| 中远景 | 极少量成组碎岩，大小与方向有关联；与天体建立尺度线索 | 不像随机撒满屏幕的多面骰子；不给背景碎片危险弹丸的颜色和速度 |
| 战斗层 | 玩家、敌机、弹道和短促命中特效 | 最高辨识度；中心保持安静，完整 XY 战场始终可见 |
| 边缘近景 | 一到两处可选岩体侧缘，缓慢旋转暴露面变化 | 继续走安全区；窄屏不足就移除，不挤压战场，不跨过触控按钮 |

纵深来自景别尺度、遮挡、色彩衰减、不同层的运动速率和真实形体转面。稳定战斗镜头下，不靠镜头乱动制造视差；远景允许极慢漂移，中景稍快，近景有克制的转动。所有装饰时间遵守暂停/恢复，不消耗规则随机数。

### 8.2 两关形成不同的场景节奏

- **初次接触：蓝色晨光轨道。** 左上浅冷云带，右上偏暖行星边缘，背景岩体少；玩家白色轮廓和 Scout 橙色清楚脱离背景。
- **交叉火力：紫色暮光碎岩带。** 更深的蓝紫空间、较低饱和暖色环光、两侧成组碎岩；保持 Raider 与 Guardian 的明度识别，不能只给第一关贴图叠紫色滤镜。

沿用 `visualTheme` 和严格校验链路。未来若增加纯视觉配置，应有有限字段和默认兼容，不把敌阵、射速、波次等规则搬进场景脚本。资产优化同时检查宽屏、4:3、手机横竖屏裁切，不让天体的主轮廓在手机上变成无法理解的色块。

## 9. 动作响应：建立一套能看懂的表演语言

以下是**样板调试起点**，不是已经验证的最佳数值。时间以毫秒描述观感，实施时运行态转换为权威 tick / 事件年龄；输入与逻辑位移不等待动画。优先用局部零件和宽高光变化显露动作，避免只加全机 roll。

| 场景 | 起势 | 主动作 | 收势及建议节奏 |
| --- | --- | --- | --- |
| 玩家起步 | 输入当帧位置改变，0～70ms 喷口伸展、外侧翼片先动 | 70～160ms 机身向运动方向侧倾，pitch/yaw 展示厚度 | 160～260ms 收到巡航姿态；机身中心无额外 XY 滞后 |
| 玩家松键 | 逻辑立即停止，0～80ms 控制翼反向，喷焰先收 | 80～180ms 一次小幅反向承力 | 180～300ms 回中；只允许一次过冲，不能晃成橡皮玩具 |
| 玩家换向 | 不做长蓄力、不延迟反向；先有翼片/喷口响应 | 身体经过中立位再进入另一侧姿态 | 约 180～280ms 建立新平衡，不以整机旋转 180° 表示换向 |
| 玩家开火 | 事件当帧短闪，武器局部回缩 | 约 40～90ms 回弹，喷口有弱伴随响应 | 约 120ms 内回位；不让连发每次都把整机剧烈点头 |
| 玩家受击 | 命中事件当帧局部暖闪、护盾/机壳短促变形 | 80～180ms 机身一次受力姿态，碎屑远离弹道中心 | 回到可瞄准姿态；无敌状态不必频繁让整机消失，可比较保留剪影的方案 |
| Scout 巡航/折返 | 单眼缓慢扫视，短翼有轻微相位差 | 折返时翼片先变、壳体跟随；眼球看向新的运动方向 | 约 180～260ms 收回；不把编队 XY 横移变成自由飞行 |
| Raider 开火 | 不增加事前蓄力或提前泄露逻辑随机选择 | 已发射的对应武器舱后坐，另一侧维持稳定 | 约 100～220ms 分层回位，发射数仍完全由引擎决定 |
| Guardian 装甲受击 | 击中区域甲片内压、核心短暗 | 约 100～200ms 重型甲片回弹 | 回稳更慢但位移更小；死亡才解体，不提前演死 |

待机动作要节制：喷口内部、单眼微转和缓慢的受光变化足够；不要让整支敌阵像果冻一样同时呼吸。机型差异主要体现在质量、频率、部件和恢复节奏，而非换一个正弦系数。

**命中与显示一致性：** 逻辑根、弹丸中心和发射点不动；姿态幅度要通过投影包围盒约束。武器活动行程围绕原发射锚点设计，不能在左右双炮视觉位置生成与真实单发中心矛盾的假弹道；必要时保留中央真实炮口，双舱只做机械响应。装饰尾迹不改变子弹看起来的到达时间。

## 10. 子弹、命中与击毁：从“有特效”变成“有结构结果”

- **玩家弹丸：** 保留方向清楚的短光矛，明亮核心与极短尾迹分层；尾迹上限由弹速与屏幕尺度约束。敌弹使用较胖的暖色尖头/胶囊剪影，形状和移动方向共同区分敌我。
- **发射：** 炮口短闪、局部武器后坐与短促音效同一事件触发。闪光约 30～70ms，不用长寿命光球堵住瞄准线。
- **装甲命中：** 局部火花朝外射出，甲片短回弹，核心亮暗改变；不每次放一个大圆圈。反馈应保留 Guardian 尚未击毁的状态。
- **击毁三段式：** 0～60ms 小范围明亮冲击；60～180ms 拆出两三块与该机型相符的壳/翼/炮舱；180～450ms 有方向地旋转、衰减和消散。轻型更快，厚甲可稍慢，但残骸永远不是额外危险单位。
- **连续击毁：** 先保证敌弹与玩家轮廓，再分配残骸和火花预算。优先减掉远离注视区的装饰粒子，保留命中瞬间，不让多次爆炸变成遮挡屏幕的烟墙。

复用现有实例池与事件去重；后续可给每型增加少量共享残片几何，并继续实例化。72 粒子现有上限先作为预算起点，不为“更震撼”直接翻倍。真实视觉收益与渲染开销一起评审。

音效只作反馈辅助：沿用事件和首次用户手势解锁机制，后续可调整轻重层次与音量包络，不在本轮新做大型音乐工程，也不把未经人耳评价的程序输出写成听感通过。

## 11. 过场与镜头：先有分镜，再有参数

### 11.1 先守住一个现实边界

现有 `START` 后规则已经运行，`wave-started` 也不等于一个可任意暂停玩法的过场窗口。仅改渲染层，不能偷偷插入倒计时、冻结敌弹、隐藏可命中目标或等待动画回调才推进下一波。

因此把演出分成两类：**ready / 终局可用真正的镜头段落；running 保持战斗镜头与可见目标稳定，只做局部演出。** 以后若用户要一个“先播入场、再正式开打”的独占流程，应另行评估与授权，不混入本轮纯美术返工。

### 11.2 建议分镜

| 时机 | 分镜与动作 | 时间草案 | 操作与安全边界 |
| --- | --- | --- | --- |
| 首屏 ready | 默认战场稳定；玩家机在展示副本中短暂转出 3/4 体积，喷嘴点亮后回到战斗姿态 | 自动展示一次约 1.2～1.6s | 开始按钮始终可点；点击后立即丢弃展示姿态，不能让规则运行时继续偏离瞄准；减少动态时直接静态 |
| 按下开始 | 镜头保持正式战斗姿态，玩家翼片展开、喷口由待机转巡航，敌机局部启动 | 约 200～350ms | 输入立即生效，敌人完整可见；不强推现有小幅运镜更大化 |
| 新波次运行中出现 | 天体边缘光缓慢变化，敌机眼/武器/装甲依次启动；极简波次字样短入短出 | 约 450～650ms | 不让整排机体从屏外飞到已经生效的 hitbox；不遮挡、错位或提前演出下一波敌人 |
| 通关 | 最后一架敌机解体；玩家喷口收束、机翼一次舒展；镜头缓慢移到玩家所在区域的展示副本，露出 3/4 侧面与宽高光；最后给结算文字 | 约 1.2～1.8s | 只在 won 权威终局后使用明显镜头变化；重新开始随时可点并取消整段 |
| 失败 | 保留玩家最后位置的显示残骸/受损副本，局部熄火、一次倾侧，镜头轻退，结算淡入 | 约 0.9～1.3s | 不让玩家仅因 `lost` 立刻消失；不追加扣血或爆炸伤害；不做持续抖屏 |
| 重置/切关/失焦 | 清空展示副本、动作阶段、残片和镜头偏移 | 当帧归位 | 不把上一局副本带入下一局；暂停/隐藏不积累待补播时间 |

“展示副本”只是在规则不活动时为演出保留的渲染对象，不是第二个玩家；生命周期复用共享资产、显式取消。结算文字不遮住表演主体，不能用巨大字幕和光圈替代动作。

## 12. HUD、触控与视觉尺度

继续铺满视口，战斗态只保留分数、生命、波次/关卡和暂停。标题与设置在非战斗态更清楚，在战斗态弱化；统一字重、间距与数字节奏，不增加技术标签、霓虹边框和嵌套卡片。

手机横屏优先检查玩家机与弹道的有效尺寸，触控按真实手指区域和安全区安排，按下反馈要轻且明确。竖屏完整显示 36×24 世界，允许上下安静留白，不通过裁切或改变规则比例强行填满。若研究两种显示布局，应分别测量主体 CSS 像素和触控遮挡；不能把高 DPR 当成“大而清楚”。

任何光环、镜头缩放、生命反馈、结算文字都与当前真实投影共享坐标。沿用 #82 已修好的玩家安全带，不让返工重新把暂停/重置盖到机身上。

## 13. 落地边界与复用清单

| 继续复用 | 后续建议返工 | 暂不做 |
| --- | --- | --- |
| 纯 TS 引擎、GameEvent、tick、种子、JSON、输入协议 | 模型的大形与局部可动结构、材质受光关系 | 新玩法、z 轴移动、三维命中、物理引擎 |
| 正交默认、等比世界投影与安全区 | 背景艺术构图、触控视图边距研究 | 战斗自由镜头、追逐相机、实时斜俯视 |

| 全屏 HUD、触控、音频解锁和本地排行 | ready/终局镜头、文字与角色的时间关系 | 新排行榜、账号、运行时 CDN、资源外链 |

运行态动作以 `tick`、事件 tick 和 ID 派生；终局后权威 tick 不再推进，终局演出使用可暂停、可取消、隐藏不补帧的展示时间线，复用现有相机导演的生命周期思想。暂停表现、事件去重、重置、恢复、减少动态效果均是样板的一部分，不在每个模型里各开一套 RAF 或定时器。

优先扩展现有 `PlayerShipMotion`、`EnemyShipMotion`、`CombatFX`、`CameraDirector` 和主题接口。需要新模块时按真实职责拆分，不为本提案预先创建空壳。动画输出控制零件姿态/局部材质，不回写快照，不让展示完成回调决定命中、积分或胜负。

敌机局部动作优先更新对应零件的实例矩阵；单机受击的颜色/亮度若需要独立变化，应使用实例属性等可合批方案，不能直接修改共享材质而让全编队一起闪。即使未来引入 GLB，也先验证刚性零件拆分与现有实例化的兼容性，不默认给每架敌机独立材质、骨骼和 AnimationMixer。

## 15. 验收方法：艺术结果和技术结果分别回答

### 15.1 必须能看的艺术证据

固定关卡、种子、运行 tick / 事件段落、画质档位及浏览器版本；主对照为当前 P4 基线与新样板，P3 仅作历史补充。全画幅证据与近景分开标记，不用放大近景代替战斗效果。

- 1920×1080、1440×900 正常战斗；390×844 与 844×390 浏览器布局；实体设备另外登记。
- 玩家 idle → 左右起步 → 松键 → 快速换向 → 连发 → 受击；三种敌机巡航、折返、开火、装甲命中和击毁的连续帧/视频。
- ready → 开始 → 新波次 → 胜利/失败 → 重置完整片段；正常速度观看，并提供少量关键帧检查变形与遮挡。
- 同条件原图、前后实际 WebGL 截图、素材源与来源说明。ReactMono 是新的学习参照，不冒充缺失的原始第二张概念图。

人工审查重点：飞船是否像有厚度的完整对象；单眼/双炮/厚盾是否一眼辨识；按键响应是否有力量且干净；爆炸是否看得懂且不遮弹；背景是否有景别而不抢戏；结算是否由角色表演成立。出现“近景漂亮、战斗仍像小图标”“只看出粒子更多”“角色动作依然难以察觉”均应明确返工。

### 15.2 技术约束与预算草案

预算是后续样板的初始目标，**不是本次测量结果或既有通过标准**：

| 项目 | 初始目标与核验方式 |
| --- | --- |
| 规则回归 | 固定输入/种子下的快照、弹道、命中、分数、胜负与原版一致；不改 `src/core/` 及关卡数值 |
| 对齐与遮挡 | 原根节点投影不变；记录姿态包围盒、炮口与子弹中心；战场四边与触控带无装饰遮挡 |
| FPS | 实体桌面目标稳定 60fps；手机高档目标 60fps、降级档目标 30fps，报告设备、分位帧时与测试时长，不只平均值 |
| 资源增长 | 先记录 P4 基线；常规编队静态绘制调用尽量不增加，增量建议不超过 20%；爆炸成本按批次控制；连续重置/切关 10 次不持续累积 GPU 资源 |
| 资产 | 单关新增压缩视觉资源以不超过约 2MB 为样板目标；背景单图约 300KB 起评；报告解码尺寸、GPU 纹理内存和首屏网络体积，而非只看 WebP 文件大小 |
| 生命周期 | 暂停/隐藏冻结或明确清理，恢复不突跳；重置取消演出；上下文丢失/恢复无重复循环与泄漏 |
| 降级 | 先减装饰残片、环境贴图尺寸与可选辉光，保留主机型剪影、危险弹丸和关键命中反馈；减少动态不等于取消必要危险提示 |

纯逻辑/姿态测试、生产构建、浏览器交互、Pages 线上、真实硬件和人眼审美分别记录。软件 Chromium 只能证明该软件渲染环境中的结果，不能替代 #70，也不能让 #69 自动通过。
